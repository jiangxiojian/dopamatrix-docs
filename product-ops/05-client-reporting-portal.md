# 客户报告网页

> 更新时间：2026-08-19
> 状态：规划草案

## 目标

当前 RPA 专项只负责客户报告网页 V1。V1 不是完整客户门户，而是把脚本已经沉淀的发布数据变成可打开查看的报告页，让甲方先回答两个问题：

1. 我们给他生产和发布了什么？
2. 哪些内容已经成功发布，帖子链接和状态是什么？

播放、互动、询盘、成交和爆款洞察先作为待补指标占位，不由当前 RPA 专项负责采集。当前直接数据源是：

```text
customer_report_seed.csv
customer_report_overview.csv
publish_summary.csv
publish_plan.csv
```

## 页面结构

第一版客户报告页只做三个视图：

```text
1. 数据总览
2. 内容与发布
3. 待补数据与异常
```

后续完整客户门户可以再加，但不属于当前 RPA 专项：

```text
询盘中心
创意洞察
周报/月报
客户登录和权限
账号健康
发布异常
数据同步状态
归因待确认池
客户反馈完成率
```

## 通用筛选

所有页面应支持：

```text
日期范围、客户、活动、产品、平台、账号、地区、内容类型
```

当前 V1 是本地/静态报告页，先按 `client_id` 在 CSV 里筛选或生成独立报告文件。完整登录、权限和多客户隔离由正式产品门户负责。

## 总览指标

| 指标 | 含义 |
| --- | --- |
| 生产内容数 | 期间完成的视频、图片、轮播或图文数量。 |
| 发布内容数 | 实际成功发布的帖子数量。 |
| 发布成功率 | 成功发布数 / 计划发布数。 |
| 总播放/展示 | 平台给出的曝光指标。 |
| 总互动 | 点赞、评论、收藏、分享。 |
| 原始询盘 | 评论、私信、表单等所有可能线索。 |
| 有效询盘 | 去重并确认有采购意向的线索。 |
| 报价数 | 已进入报价阶段的线索。 |
| 成交数/成交额 | 需要甲方或销售回填。 |
| 询盘转化率 | 有效询盘 / 播放或展示。 |
| 单帖平均询盘 | 有效询盘 / 已发布内容数。 |

每个指标都要同时展示：

- 当前值。
- 较上期增减。
- 与目标的完成度（如果有目标）。
- 数据最近同步时间。
- 数据来源：平台 API、脚本、人工回填或客户反馈。

## 内容与发布

应该展示：

- 计划生产数量。
- 实际完成数量。
- 审批通过/驳回/待处理数量。
- 已交付未发布数量。
- 已发布数量。
- 平均生产耗时。
- 平均修改次数。
- 按产品、账号、平台的分布。

每条内容至少展示：

```text
封面缩略图
标题
内容类型
对应产品
creative_id / video_id
审批状态
发布状态
平台
账号
帖子链接
发布时间
```

## 内容表现

本节是未来方向。当前 RPA 专项只在页面里保留播放、互动、链接点击、询盘等待补字段，不负责采集平台表现和线索数据。

视频指标：

- 播放量。
- 触达人数（平台提供时）。
- 2 秒或 3 秒观看。
- 平均观看时长。
- 平均观看比例。
- 完播率。
- 重播率（平台提供时）。
- 点赞、评论、收藏、分享。
- 主页访问。
- 链接点击。
- 私信和询盘。
- 异常审核或负反馈。

图片、轮播和图文指标：

- 展示量。
- 触达人数。
- 互动。
- 收藏和分享。
- 主页访问。
- 链接点击。
- 询盘。

页面必须展示完整漏斗：

```text
曝光/播放
-> 有效观看或互动
-> 主页访问 / 链接点击 / 私信 / 表单
-> 原始询盘
-> 有效询盘
-> 报价
-> 成交
```

高播放但没有询盘的内容，不应该自动被视为更优。

## 询盘报告

本节不属于当前 RPA 专项。V1 报告页只展示 `lead_pending_count` / `metrics_pending_count` 等待补状态，不实现询盘中心、客服流转或线索分配。

询盘要分层，不要只报一个总数。

| 层级 | 定义 |
| --- | --- |
| 原始咨询 | 用户发过评论、私信、表单或 WhatsApp 消息。 |
| 待确认询盘 | 用户意图或所问产品尚不明确。 |
| 有效询盘 | 产品、地区、需求等基本信息已确认。 |
| 合格商机 | 符合目标市场和客户要求。 |
| 已分配 | 已交给正确客户或销售。 |
| 已联系 | 销售已经响应。 |
| 已报价 | 已给正式报价。 |
| 已成交 | 客户确认成交。 |
| 无效/重复 | 广告、骚扰、重复客户或没有真实需求。 |

每条线索至少展示：

```text
来源平台、来源账号、来源帖子、关联视频、
关联产品、客户原始消息、首次联系时间、
国家/地区、联系方式、归因方式、归因可信度、
负责人、当前阶段、无效原因、处理记录
```

## 归因显示

本节是完整客户门户方向。当前 RPA 专项只负责把 `tracking_url`、`attribution_token`、`post_url` 和 `platform_post_id` 写入报告数据源。

报告里要明确展示归因可信度：

- `确定归因`：表单、帖子或 token 能直接识别来源。
- `高可信归因`：通过 WhatsApp、Telegram 或产品链接进入。
- `人工确认`：客服询问后，用户确认看过某条内容。
- `账号级归因`：只能确认来自某个账号，无法确认具体帖子。
- `来源未知`：证据不足。

对于共享账号：

- 甲方只能看到与自己 `client_id` 相关的内容和线索。
- 不向甲方展示其他客户的产品、线索和联系方式。
- 模糊询盘先放在共享待确认池。
- 确认产品后再分配给对应甲方。
- 共享账号总量必须标明是“账号总量”，不是“某个客户专属量”。

## 创意洞察

本节不属于当前 RPA 专项，后续由增长产品或爆款基因模块承接。

这部分是爆款基因学习的桥梁。应展示：

- 本期最好的帖子。
- 按播放表现最好的帖子。
- 按有效询盘表现最好的帖子。
- 按询盘转化率最好的帖子。
- 最有效的 Hook。
- 最有效的产品切入点。
- 最有效的长度区间。
- 最有效的 CTA。
- 内容疲劳迹象。
- 下一轮准备测试什么。

每条洞察都要标注：

```text
观察到的相关性
经过对照实验验证
样本不足
```

不要拿几个样本就宣称找到了“必爆公式”。

## 周报/月报

周报/月报可在客户报告网页 V1 稳定后再做导出草案；询盘质量、销售反馈和成交数据不由当前 RPA 专项采集。

网页是实时查看用的，周报/月报是复盘和汇报用的。

周期报告至少包含：

- 概览。
- 本期完成的生产和发布。
- 性能变化。
- 询盘质量和销售反馈。
- 最优内容。
- 问题和异常。
- 下周期计划。

导出的 PDF/Excel 必须和网页共用同一个数据库。

## MVP

当前 RPA 专项的第一版应先保证这些数据真实可靠：

1. 生产数、交付数、发布数和发布成功率。
2. 帖子链接、平台 post id、发布时间和发布状态。
3. 按客户、产品、平台、账号和内容类型的汇总。
4. 每条内容的素材、标题、文案、追踪短链和截图/发布证据。
5. 待补指标：播放、互动、询盘、成交等先展示为空或待同步。
6. 最近同步时间和数据来源。

短期桥接数据源先用 `publish_summary.csv`，再叠加 `customer_report_seed.csv` 和 `customer_report_overview.csv` 作为报告网页和周报/月报的输入口径。

后续再由其他专项接入询盘中心、客户权限系统、爆款基因图、成本、收入和 ROI。
