## 目标

把比特浏览器验证脚本推进到运营可用的发布工具：现行版本提供半自动发布，后续增加经过批次批准的自动提交和定时发布。

第一阶段目标仍然很克制：

```text
读取发布计划 -> 选择账号环境 -> 打开 TK/FB 发布页
-> 上传素材 -> 填文案 -> 截图和日志 -> 人工确认发布
```

现行版本的最终发布按钮仍由人工点击。2026-11-20 已登记后续自动发布需求并开始 A0 入口观察：正常任务获批后自动执行，验证、账号异常或结果不明时暂停并交人工。详细范围、优先级和验收见 [16-rpa-auto-publishing-plan.md](./16-rpa-auto-publishing-plan.md)；自动发布和真正的定时能力尚未启用。

现行半自动版本的收口重点如下；后续自动发布作为独立实施阶段管理：

| 重点 | 要做到什么程度 | 不做到什么 |
| --- | --- | --- |
| 客户报告网页 V1 | 读取 `customer_report_seed.csv` / `customer_report_overview.csv`，生成可打开查看的报告页，展示发布明细、成功率、帖子链接、账号/平台/客户/产品维度和待补指标。 | 不做完整登录权限、客户门户、多租户后台和询盘中心。 |
| 发布回收和稳定性 | 继续补 TK/FB 发布后 URL 回收、异常分类、弹窗库和更多实机样本，让运营知道每条任务是已发布、待人工、可重试还是要换号处理。 | 当前版本保持人工发布；自动提交与定时另行实施，不做刷量或绕验证。 |

## 后续规划：批量运行与集中审核

> 状态：整体需求已登记，尚未完整实施。以下保留人工发布模式的规划；队列、恢复和通知与 [自动发布计划](./16-rpa-auto-publishing-plan.md) 共用基础，自动模式按该计划单独验收。

### 目标

客户可以在非工作时间提交内容。DopaMatrix 生成并交付投放包后，发布脚本能够按队列逐条准备草稿、保存截图和结果；运营不必全程守在电脑前，而是在批次完成或遇到需要介入的情况时查看通知，再集中审核待发布内容和异常任务。

```text
客户提交需求
-> DopaMatrix 生成内容并交付投放包
-> 发布任务进入待处理队列
-> 脚本按计划顺序准备草稿并记录结果
-> 待人工审核 / 异常待处理
-> 运营集中检查并手动发布或退回
```

视频生成和投放包制作由 DopaMatrix 产品流程负责；本发布脚本的起点是“投放包已准备好”。两边可以通过文件交付和状态约定衔接，但不能把视频生成耗时算成发布脚本已具备的自动化能力。

### 运营原则

| 场景 | 规划规则 |
| --- | --- |
| 常规客户任务 | 进入队列等待下一个运营处理时段，不承诺夜间即时发布；对外响应时间应按团队实际处理时段约定。 |
| 夜间批次准备 | 允许脚本在预定时段连续准备任务，运营无需逐条守候；完成后统一查看“待人工审核”和“异常待处理”。 |
| 最终发布 | 保持人工确认，不自动点击 TikTok / Facebook 的最终发布按钮。 |
| 验证、登录或平台风险提示 | 暂停相关账号的后续任务并通知人工检查；不自动绕过验证码、人脸验证或安全限制。 |
| 加急任务 | 只有明确提供并安排值班人员时才承诺非工作时段响应；是否收费属于运营/商务规则，不由脚本默认承诺。 |
| 运行环境 | 批次运行依赖电脑保持唤醒、BitBrowser 和目标环境可用、网络稳定。电脑睡眠、应用关闭、断网或 Windows 锁屏期间能否继续运行尚未验收，不能在验证前承诺。 |

### 建议的队列与状态

- **待准备**：投放包已就绪，任务等待脚本处理。
- **准备中**：脚本正在处理单条任务；同一浏览器窗口仍按顺序使用，暂不规划并发操作同一环境。
- **待人工审核**：草稿、文案和截图已准备，等待运营判断并手动发布或退回。
- **异常待处理**：登录失效、验证码、代理/网络故障、上传失败或页面变化等需要人判断的任务。
- **已发布 / 已拒绝 / 已跳过**：由人工确认后记录最终结果，保留现有计划表状态及回填规则。

这些是队列视图的业务状态建议，不表示当前 CSV 状态机已经包含全部状态。实施时应先核对现有状态字段，避免为相同含义重复造状态。

### 分阶段实施与验收

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| Q1：批次队列 | 工作台展示整批数量、当前进度、已准备、失败和待审核数量；支持安全暂停，记录每条任务结果。 | 混合 TK/FB 批次中的单条普通失败不会静默丢失；其余任务按既定策略继续或明确停止。 |
| Q2：失败隔离与恢复 | 结合现有单任务硬超时，实现批次中断后的可恢复执行、失败跳过/重试和重复执行保护。遇到账号验证或安全提示时暂停该账号，不盲目重试。 | 重启后能识别已完成任务，不重复准备或误覆盖已发布任务；每次重试有记录。 |
| Q3：集中审核与通知 | 提供“待人工审核”和“异常待处理”视图，并在批次完成或出现需介入异常时发送批次摘要通知。 | 通知包含批次标识、任务数量、待审核数、异常数和工作台入口；正常的逐条进度不刷屏。 |
| Q4：运行时段与容量 | 根据实测任务耗时、账号发布限制和运营班次设置处理窗口、并发上限及普通/加急服务规则。 | 以真实素材和账号测出吞吐量，再制定可兑现的服务时段；未经实测不承诺固定批次完成时间。 |

### 当前边界与风险

- “不需要一直盯着”不等于“任何情况下都无人值守”：脚本只能自动处理可预期步骤，平台验证、账号状态变化和未知 UI 必须留给人工。
- 先实现可观测、可暂停、可恢复的顺序队列，再评估跨窗口并发；不能为了速度牺牲账号、平台和内容之间的对应关系。
- 运行期间需要有结束/异常通知和明确的接手人；若没有人处理异常，任务应保持暂停状态，而不是无限重试。
- 先用内部测试包验证夜间长批次、断网、BitBrowser 退出、单条超时和重新启动后的恢复行为，再考虑客户 SLA。
- 当前版本仍需人工点击最终发布；后续自动模式的批次批准、提交确认和异常处理按自动发布专项实施，登记需求不表示现版已经改变行为。

建议新增：


```powershell
python docs/scripts/publishing/bitbrowser_rpa_example.py `

  --delivery-dir "E:\project\dopaMatrix\dopamatrix_delivery_1781700321(1)" `
```

## 状态机

| 状态 | 含义 |
| --- | --- |
| `READY` | 已生成发布计划，等待脚本处理。 |
| `RUNNING` | 脚本正在打开窗口、上传素材或填写文案。 |
| `PREPARED` | 脚本已准备好草稿，等待人工检查发布。 |
| `FAILED` | 脚本执行失败，需要人工判断是否重试。 |
| `SKIPPED` | 主动跳过，例如账号不可用或排期未到。 |
| `PUBLISHED_MANUAL` | 人工确认并发布，已记录帖子链接或截图。 |
| `REJECTED_MANUAL` | 人工检查后决定不发布。 |

## 平台安全边界

1. 当前版本不自动点击最终发布按钮；后续仅对明确批准的内容版本实施自动提交，详见自动发布计划，尚未实施。
2. 不绕过验证码、人脸验证、安全检查或平台限制。
3. 不做刷粉、刷赞、刷评论、账号互导等动作。
4. 新号测试控制频率，先一条一条跑，不连续高频重试。
5. 平台弹窗涉及账号级设置时默认暂停，例如 TikTok 自动内容检查。
6. 同一个比特窗口可以测试 TK + FB，但批量执行时只顺序跑，不并发操作。
7. 同窗口多平台时必须保持 Tab 隔离，默认每条任务新开 Tab；复用已有 Tab 只用于临时调试，避免后一条任务覆盖前一条草稿。
