# 文档维护规范

> 更新时间：2026-07-27  
> 文档类型：内部规范  
> 状态：草案

## 目的

`product-ops` 目录用于记录 DopaMatrix 从“内容生产工具”走向“发布、询盘、报告、增长学习闭环”的产品运营规划。这里的文档要能被产品、运营、研发一起维护，所以需要统一结构和状态。

## 文档类型

| 类型 | 用途 |
| --- | --- |
| 索引 | 告诉读者从哪里开始读，哪些问题在哪篇文档里。 |
| 方案 | 描述某个模块的目标、边界、数据结构和 MVP。 |
| 决策记录 | 记录已经形成的关键判断，以及为什么这么决定。 |
| 待办清单 | 把规划拆成可执行任务和待验证假设。 |
| 变更日志 | 记录文档本身的结构性变化。 |

## 状态枚举

| 状态 | 含义 |
| --- | --- |
| 草案 | 讨论整理，方向可用，但还可能调整。 |
| 待确认 | 需要负责人、客户或技术验证后才能定。 |
| 已决策 | 团队已经采用，后续实现应按此执行。 |
| 实施中 | 已进入开发或运营落地。 |
| 已落地 | 已在流程或系统中稳定使用。 |
| 已废弃 | 不再使用，保留用于历史追溯。 |

## 标准文档头

新文档建议使用这个头部：

```md
# 文档标题

> 更新时间：YYYY-MM-DD
> 文档类型：方案 / 决策记录 / 待办清单 / 规范
> 状态：草案 / 待确认 / 已决策 / 实施中 / 已落地 / 已废弃
> 适用阶段：试点 / V1 / V1.5 / V2
> 相关文档：[文档名](./path.md)
```

如果暂时没有负责人，不要虚填。等团队明确责任人后再补。

## 决策记录格式

关键产品判断写入 [DECISIONS.md](./DECISIONS.md)，格式如下：

```md
## DEC-YYYYMMDD-序号：标题

| 字段 | 内容 |
| --- | --- |
| 状态 | 已决策 / 待确认 / 已废弃 |
| 日期 | YYYY-MM-DD |
| 背景 | 为什么需要这个决策 |
| 决策 | 我们决定怎么做 |
| 影响 | 会影响哪些模块或流程 |
| 后续 | 需要验证或执行什么 |
| 相关文档 | 链接 |
```

## 待办规则

待办写入 [TODO.md](./TODO.md)。每个事项要有：

- 优先级：`P0`、`P1`、`P2`。
- 阶段：`Phase 0`、`Phase 1` 等。
- 状态：`未开始`、`进行中`、`阻塞`、`完成`。
- 产出：可检查的文档、表结构、脚本、页面或测试结果。

不要把一句大愿景写成待办，例如“做 AI 客服”。应拆成“定义线索状态机”“人工录入线索”“AI 回复草稿只读知识库”等可执行项。

## 变更日志规则

结构性更新写入 [CHANGELOG.md](./CHANGELOG.md)，例如：

- 新增或删除文档。
- 修改阅读顺序。
- 某个规划从草案变为已决策。
- 重要边界变化。

普通错别字和小句子调整不必逐条记录。

## 维护原则

1. 一个文档只解决一个边界清晰的问题。
2. 新讨论先找最小相关文档更新，不要全塞到 README。
3. 涉及执行取舍的内容要同步写入决策记录。
4. 涉及研发、运营或客户动作的内容要同步写入 TODO。
5. 明确区分“已实现”“规划中”“待验证”。
6. 不把平台风控绕过、虚假互动、混淆客户归属写成产品目标。
